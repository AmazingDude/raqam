## Financial representation and states

- JSON money is a base-10 **integer paisa string**: `10005` means PKR 100.05. Database amounts use nonnegative bigint and must be read as text, never JavaScript numbers. Totals use BigInt internally; serialized net movement can be negative.
- CSV amount is a decimal string with at most two decimal places; direction carries the sign. Explicit zero is allowed. Unknown, blank, negative, excess-precision or unparseable amounts stay invalid, never zero. The template does not accept thousands separators or exponent notation.
- Dates use valid `YYYY-MM-DD`. Template/workspace currency is PKR; an unsupported currency column is rejected. OCR currency preserves original evidence or null, never an assumed PKR value.
- Only an accepted category is attached to a transaction; pending category values live in proposals. Import, category review and matching have separate states. A receipt never becomes a cash transaction.
- C uses `categorySuggestionSchema`/`matchSuggestionSchema` for raw AI output: no owner/proposal ID and only proposed/needs-review state. Full stored-proposal schemas include accepted/rejected history after user review. A's wrapper must scope every referenced record and assign ownership/IDs independently of the model.
- Extracted/corrected document fields remain separate and preserve nulls. User-confirmed D13 requires valid date, exact total and explicitly confirmed PKR for document acceptance; merchant/reference may remain unknown. Explicit zero is valid; unknown is not zero. This does not infer currency or prove settlement.
- Source references carry source ID and logical CSV row number (header is row 1). Preview also preserves physical line numbers for multiline fields. Supporting images have a null row number.
- Hashes cover exact source bytes; database identity is unique per workspace/type/hash and source/row. Equal-valued distinct rows remain legitimate. CSV registration/confirmation implement repeat detection; cloud Storage behavior remains to verify. Failed uploads recover only when the exact owner-scoped hash path is visible through Storage object metadata.

## Proposed accrual-ledger contract (v0.1; review required)

The user selected accrual double-entry, PKR integer-paisa amounts, service-delivery/goods-received recognition dates, a user-selected history range, supported opening balances when needed, a direct cash-flow statement from reviewed cash movements, and a review-only clearing account for unclassified bank activity. This remains a **Person 1 proposal**, not a frozen team contract. Person 2 review and the remaining Gate 0 details are still required before persistence/API implementation consumes it. Proposed limits: a neutral account-type model with no legal-entity preset or accounting-standard claim; report coverage is complete only when the selected range is covered, all required source kinds are present, and needed opening balances are supported.

The proposed runtime schemas are in `src/lib/contracts/ledger.ts`. `ledgerAccountSchema` describes stable account IDs/types, reporting roles, cash status, active state and optimistic version; `ledgerAccountCommandSchema` omits workspace ownership and requires ID/version to appear together on updates. `ledgerJournalDraftSchema` represents a proposed entry with a complete set of source links (including supplier bill and customer invoice), an optional single cash-movement identity, recognition-date evidence, optional reversal link/reason, PKR currency and lines. Evidence locators identify a statement row, document field/page, or owner decision without copying source text. A revenue/expense journal requires an owner-reviewed effective date with a locator tied to one of its linked sources; missing dates remain review exceptions and cannot pass trusted command validation. It rejects a non-positive/unbalanced journal, invalid amounts and duplicate line IDs. `validateLedgerJournalCommand` additionally requires authenticated server-supplied workspace scope, active in-scope accounts, supported source records, recognition evidence, and current record versions; never accept its trusted context from a browser or model. `ledgerJournalBatchSchema` rejects incomplete/duplicate batches and duplicate cash-movement postings within the batch. Durable idempotency and uniqueness still belong in the database transaction, not this in-memory contract.

Posted journals are immutable. Correcting one means a separately reviewed, linked reversal with a reason, an exact inverse of the posted lines, and a correcting journal; the trusted command seam rejects a missing/foreign/already-reversed target or a non-exact inverse. Do not rewrite posted lines. The `cashMovement` field identifies exactly one bank transaction or explicitly recorded manual payment; source links can also point to an invoice/document. An import linked to a manual payment must reuse that same cash movement and must not create another posting. A source-document approval without settlement has no cash movement. Source/account existence and tenant ownership are checked against server-loaded records before any write.

Reports use an as-of date for trial balance/balance sheet and inclusive `from`/`to` periods for income/cash-flow statements. Cash-flow uses `method: "direct"`; only reviewed cash movements with explicit operating/investing/financing classification enter classified totals. An unclassified movement stays in review-only clearing and is excluded from classified subtotals while remaining visible as unresolved. The deterministic server calculations produce trial balance, income statement, balance sheet and direct cash flow using `BigInt` only; current-period earnings are included in balance-sheet equity, and cash-flow net change is compared with the net change in cash-account journal lines. A mismatch is exposed as `reconcilesToLedger: false`, never hidden. `ledgerHistoryCoverageSchema` carries the selected range, available coverage, missing source kinds and unsupported opening-balance account IDs; an incomplete evidence set cannot claim `isComplete: true`. Trial-balance output validates row totals and debit/credit equality exactly. None of these schemas calculates or proves that hosted data is complete by itself.

Synthetic examples exercised locally: a delivered customer service accrues Dr Receivable / Cr Revenue with `cashMovement: null`; a later receipt posts Dr Bank / Cr Receivable with exactly one bank transaction identity. A goods-received supplier bill accrues Dr Expense / Cr Payable with no cash; later settlement posts Dr Payable / Cr Bank with exactly one bank movement. A bank-first unclassified outflow posts Dr review-only clearing / Cr Bank and remains visible as unresolved; later classification clears that account without creating another cash posting.

### Assistant request and answer

`POST /api/assistant` accepts only `{ question: string }` (trimmed, 1–1000 characters, JSON body at most 8 KiB). Clerk supplies identity, the server loads that owner's workspace, and the request must have the configured app Origin. No client-supplied scope, conversation history, credentials or tool results are accepted. Responses are private and `no-store`.

The adopted route/UI schema is `src/lib/contracts/assistant.ts`: `{ workspaceId, question, text, records, citations, actionTrail, partial }`. Citations contain accessible transaction/document IDs and source references, never signed URLs. The UI resolves document previews through the existing private source endpoint. Action entries describe actual executed tools and coverage; no hidden reasoning is exposed. Questions survive failures and in-flight requests are cancelled on screen/account changes.

The model chooses tools and then selects observed result IDs using a small validated JSON response. Code renders all returned financial claims, amounts, counts and references. Arbitrary model prose, invented result IDs and mutable/foreign tool arguments never become an answer. Failed finalization, exhausted rounds and paginated/truncated observations produce a labelled partial answer or clarification. Unresolved import counts always cover the whole workspace even when cash dates are filtered. Repeated identical tool requests reuse the same request-local observation.

Each request has a 45-second deadline, three model rounds/total provider attempts, four unique read executions, and bounded model context. A per-instance guard allows one in-flight request and six requests per minute per owner, with a bounded 1000-entry map; this is not a distributed account quota. Document reads fail closed above 200 rows rather than claiming a partial aggregate is complete. This route uses the existing provider factory (Groq by default); it does not implement OCR/category/match route wrappers or close their release gates.

Error/status mapping: UNAUTHENTICATED 401, NOT_FOUND 404, INVALID_INPUT 422, CONFLICT 409, UNAVAILABLE 503. Mutation handlers must reject cross-origin cookie requests. Initial transaction-file guards are 1 MiB, 1–50 preview rows and 50 total workspace transactions; these are prototype guards, not measured host capacity. The proposed image cap still awaits its gate.

### Transaction import commands for B

`POST /api/imports` accepts exactly one multipart field `file`: `.csv`, `.tsv`, `.xls`, `.xlsx` or `.pdf`, up to 1 MiB. Delimited text recognizes comma, semicolon, pipe and tab separators plus UTF-8, UTF-16 and Windows-1252. Excel reads the first worksheet containing a recognizable transaction table in its first 20 rows. PDF statements must contain selectable text, have at most 10 pages, and expose a recognizable aligned transaction table; scanned/image-only PDFs and unrecognized layouts receive clear file-level errors. Common date, description, direction, debit, credit, amount, reference and currency headings are mapped. Debit/credit pairs derive direction only when one side has a clear nonzero amount. PKR amounts with common grouping/decimal separators and common bank dates are normalized to exact preview values. Formula-based values in mapped transaction columns receive a clear file-level error and must be saved as values before upload; formulas in unrelated columns are ignored. Unsupported currencies, ambiguous directions, unknown amounts and malformed rows stay unresolved; values are never silently coerced to zero. The original bytes are private and content-hashed for repeat detection. The result remains `{ importId, preview, status, confirmation, duplicate }`; upload creates no cash. `GET /api/imports/{id}` returns the same stored batch without `duplicate`. Preview retains source header/row order and raw cell values, with a bounded canonical column map and editable draft fields.

Confirmation accepts `{ rows: [{ rowNumber, action: "correct", transaction }, { rowNumber, action: "reject" }] }`. `rows` defaults to `[]`. The full corrected transaction uses `cashRowSchema` in `src/lib/contracts/imports.ts`, including exact `amountMinor` string, PKR and nullable reference. Omitted valid rows are imported; omitted invalid rows remain unresolved. Confirmation is an explicit user action. Originals remain intact. The result is `{ importId, importedCount, rejectedCount, unresolvedCount, duplicate }`.

Confirmation writes all cash/history/status in one database transaction. Repeating a completed request returns its original receipt and never reapplies changed corrections. Originals, the confirmation plan and its initial receipt remain stored unchanged. The workspace lock serializes confirmations; multi-client behavior still requires managed database validation.

After migration 004, `GET /api/imports/{id}/resolutions` returns `{ importId, rows: [{ rowNumber, outcome, transactionId }], importedCount, rejectedCount, unresolvedCount }`. Outcomes are `imported`, `rejected` or `unresolved`; only imported rows have a transaction ID. These are current cumulative counts, unlike the original confirmation receipt. Pending batches return CONFLICT until confirmed.

`POST /api/imports/{id}/resolutions` accepts `{ requestId, rows }`: a client-generated UUID and 1–50 explicit correction/rejection decisions using the same full corrected cash shape above. Only originally unresolved, still outstanding rows can be decided. Nothing is auto-imported by this command. A correction creates cash and immutable history; rejection creates history without cash. Original source fields remain intact, including unknown amounts and blank descriptions.

The result is `{ importId, requestId, correctedCount, rejectedCount, remainingUnresolvedCount, transactionIds, duplicate }`. Correction/rejection counts describe this request; the remaining count is its saved receipt. Retrying the same ID and exact decisions returns that receipt with `duplicate: true`, without overwriting later cashbook reviews. Reusing the ID with different decisions or trying to decide an already reviewed row returns CONFLICT. Use a fresh GET for current totals after other decisions. Invalid input or the 50-transaction workspace cap rolls back all cash, history and the request receipt together. Ownership is checked before retry lookup; clients cannot supply a trusted owner/workspace.

### Reviewed cashbook commands for B

After migration 003, `GET /api/transactions/{id}` returns `{ transaction, reviewVersion }`. `PATCH` accepts `{ expectedVersion, description?, category? }` with at least one change field. The category must be an explicit guide label or null; a label becomes accepted, while null clears it to needs_review. Money/date/direction/source/owner changes are rejected. Description edits preserve original fields. Changes atomically increment the version and append immutable previous/current values and actor/timestamp. An unchanged save creates no history. A stale request returns 409 CONFLICT; reload before reviewing again. An import retry never overwrites these edits.

`GET /api/transactions/{id}/reviews?limit=20&cursor=0` returns `{ items, nextCursor }` in ascending version order; each item has the shared review-decision fields plus `reviewVersion`. The cursor is the previous page's last version as a string. Category and match proposal decisions also append the affected transaction's previous/current cashbook state here. Import-row decisions remain in the import history. `GET /api/reviews?proposalId={uuid}&limit=20&cursor=0` returns the versioned proposal decision history with actor, timestamp, decision and previous/current proposal values.

`GET /api/summary` accepts optional ISO `dateFrom` and `dateTo` bounds and returns exact `CashSummary` totals, accepted-category and matched-record coverage counts, category buckets and the unreviewed remainder for the inclusive period. With no date bounds it summarizes the whole workspace. The unresolved import row count remains workspace-wide because unresolved source dates may be unknown. `GET /api/export` does not accept filters and downloads the whole-workspace `raqam-cashbook.csv` with original/reviewed descriptions, exact decimal amounts, accepted categories and review/match/source statuses; the UI states that table filters do not limit this export. `X-Raqam-Transaction-Count` reports rows exported from the same snapshot; `X-Raqam-Unresolved-Import-Rows` reports excluded rows. Both read one database snapshot under RLS and neither silently totals only the first page. Unresolved counts include invalid rows in pending imports and unresolved outcomes in confirmed imports; rejected rows are excluded. More than 50 visible cash records fails safely rather than emitting truncated financial results.

Document locks serialize review/extraction; every successful mutation increments reviewVersion and preserves immutable prior/current state/actor/time. Extraction reruns cannot overwrite corrected, accepted or rejected document decisions. Stale snapshot/version or a new attempt to propose against a reviewed category/matched document conflicts. Do not use `40001` for application conflicts. Private existing sources, extracted originals and history are never removed by a failed provider call.

A1 calls `reserve_receipt_extraction` **before inference**. Only `reserved` starts a provider call; `busy` returns a recoverable 409 and `cached` reuses the saved result without inference. A saved failed operation remains failed; explicit recovery uses a fresh request ID. The API deadline is 50 seconds, below the 60-second route duration; C's adapter caps attempts at two with SDK retries disabled. Late writes, changed identity, expired leases or stale versions conflict. Current extraction results do not replace corrected/accepted/rejected review state. Embedded Postgres tests cover evidence persistence, cache and failure replay, correction preservation, malformed/foreign writes, allowance and stale/expired completion. ### BA-00 assistant result contract v1 — adopted

Canonical runtime schemas and inferred result types are exported from `src/lib/contracts/assistant.ts`: `assistantToolResultSchemas`, `AssistantToolResult`, `AssistantSnapshot`, and `parseAssistantToolResult(name, value, expectedWorkspaceId)`. Argument schemas remain in `src/lib/contracts/schemas.ts`. A's request-bound `createScopedAssistantTools` adapter in `src/lib/server/assistant/tools.ts` is created only after session/workspace authorization and closes over that workspace. Each observation carries the exact canonical result under `details.result`; the optional result-only facade `createScopedAssistantResultTools` returns those same four payloads for consumers that need no observation text. C must not create another reader or accept caller/model ownership, SQL, URL/path, or mutation arguments.

Every result has `returnedCount`, `totalCount`, an explicit `complete`, `nextCursor` (null for non-paged results), and `snapshot: { workspaceId, token, sources }`. The 64-character SHA-256 token identifies the version of the full validated source read and canonical source list, not just record statuses. Snapshot source lists are unique. A binds the workspace into every snapshot; `parseAssistantToolResult` checks it against the current workspace. Keep the snapshot in the server-side fact registry and out of model-authored arguments/context.

| Tool | Validated payload and count meaning | Snapshot sources / completeness |
| --- | --- | --- |
| `list_transactions` | `items` are validated cashbook rows; `returnedCount` is this page size; `totalCount` is the full filtered set | `cashbook`; `complete` is true only when the un-cursored response covers the full filtered set. A later cursor page remains `complete: false`, even if it has no next cursor. |
| `get_cash_summary` | `summary` contains code-calculated exact `MinorUnits`, `currency: "PKR"`, contributing IDs/count, category totals and unreviewed totals; counts refer to every row in the date-filtered set | `cashbook`; always complete because this endpoint computes over the full scoped set. Never derive it from a list page. `dateFrom`/`dateTo` echo the inclusive request scope; unresolved imports remain workspace-wide. |
| `get_review_queue` | `kind` selects either transaction `items` or supporting-document `documents`; counts refer to the full matching queue, not the returned page | `cashbook` for category/match queues; `documents` for unresolved document fields. Paged responses obey the same first-page completeness rule as `list_transactions`. |
| `get_record_evidence` | `transactions`, `documents`, and bounded `history`; counts cover the unique requested records, and any missing/inaccessible ID fails closed | Always includes `history`, plus `cashbook` and/or `documents` when read. `complete` is false when any per-record history is truncated to the latest 20 decisions; `nextCursor` is null. |

The result `snapshot.sources` is a compact provenance marker: list/summary use only `cashbook`; queue results use the source selected by `kind`; evidence combines the reads it actually performed. C maps its proposed fact-registry inputs as follows: fact values/currency/counts come only from the parsed result payload (especially `get_cash_summary.summary`), query scope comes from the already-validated tool arguments and result `kind`/date range, source IDs/locators come from each payload record's `source`, and snapshot provenance comes from the result snapshot object. Opaque fact/reference IDs remain request-local and C-generated. A's `text`/rendered observation is explanatory, never a numeric fact source. Any `complete: false` result stays explicitly partial; no numeric aggregate may be reconstructed from `items`.
